# 會議即時英譯中字幕系統

一位英文講者 →（單向）→ 約 10 位觀眾各自用手機／電腦看台灣繁體中文字幕。

依 `即時語音英譯中字幕系統_規劃文件.md` 實作。

---

## 快速開始

```bash
node server.mjs
```

啟動時終端機會印出**房間碼**（給觀眾）和**操作金鑰**（只給你自己）。

| 角色 | 網址 |
| --- | --- |
| 操作員（收音） | `http://localhost:8787/captioner` |
| 觀眾 | `http://<你的IP>:8787/?room=<房間碼>` |

觀眾網址可以直接在收音頁按「複製觀眾網址」拿到。

## 設定

把 `.env.example` 複製成 `.env`：

```bash
cp .env.example .env
```

| 變數 | 說明 |
| --- | --- |
| `DEEPGRAM_API_KEY` | STT。[console.deepgram.com](https://console.deepgram.com) 新帳號送 US$200。**不填也能跑**，會自動退回瀏覽器 Web Speech 備援 |
| `GEMINI_API_KEY` | 翻譯。[aistudio.google.com/apikey](https://aistudio.google.com/apikey) |
| `ANTHROPIC_API_KEY` | 翻譯（替代）。兩個都填時用 `TRANSLATE_PROVIDER` 決定 |
| `STT_LANGUAGE` | 預設 `en-GB`（英國腔）。美國腔改 `en-US` |
| `ROOM_CODE` / `OPERATOR_KEY` | 不填會隨機產生。**7 天活動建議固定下來**，網址才不會每天變 |

## 架構

```
🎤 講者英文
     │
┌────▼──────────┐
│ Captioner 收音頁│  操作員筆電
└────┬──────────┘
     │ ① 跟 Relay 要 Deepgram 短期 token（300 秒）
     │ ② 直連 Deepgram WSS 送 16kHz PCM，收英文逐句
     │ ③ 逐句 POST 純文字回 Relay
┌────▼──────────────────────┐
│ Relay 伺服器（Node，零相依）│  API key 只在這裡
│  ④ Gemini／Claude 翻台灣中文│
│  ⑤ SSE 廣播 + 逐字稿存檔    │
└────┬──────────────────────┘
     │ SSE {英文, 中文}
  ┌──┴──┬─────┬─────┐
iPhone Android 筆電  …約 10 人
```

### 與規劃文件的兩處差異

文件第 4 節畫的是「音訊經過 Relay 再轉給 Deepgram」、觀眾端用 WebSocket。實作時改成下面兩點，**目的與文件一致但更好**：

**① 音訊由收音頁直連 Deepgram，不經過 Relay。**
文件擔心的是「API key 不外露」——這點用 Deepgram 的 `/v1/auth/grant` 短期 token 達成（300 秒有效，key 本身仍只在伺服器）。換來的好處是：音訊不必在會場上傳兩次（省一半頻寬）、少一跳延遲，而且 Node 端不需要自己實作 WebSocket 伺服器，維持零外部相依。

**② 觀眾端用 SSE 而不是 WebSocket。**
觀眾是純單向接收，SSE 剛好夠用，而且 `EventSource` **瀏覽器原生就會自動重連**——文件第 10 節要求的「斷線韌性」直接免費拿到，不用自己寫重連邏輯。搭配 `Last-Event-ID`，重連時伺服器會自動補送漏掉的字幕。

## 部署到 Render

本機跑只有同一個 Wi-Fi 的人連得到。要讓觀眾用自己的手機網路連，必須部署到有 HTTPS 的地方——**麥克風權限和 PWA 安裝都硬性要求 HTTPS**。

### 為什麼是 Render 而不是 Vercel

Vercel 是 serverless，它的官方文件明說「**沒有內建方法可以把訊息廣播到其他實例持有的連線**」。這個系統的核心就是「收音頁送一句進來 → 推給 10 個觀眾連線」，而在 Vercel 上收音請求和觀眾連線落在不同實例、看不到彼此的記憶體。

不是完全做不到，但兩條繞路都有代價：

- **外掛 Redis 當共享記憶體**：所有 `state` 都得搬進 Redis，而且 10 條連線一直握著 ≈ 840 GB-小時，**超過 Hobby 的 360 GB-小時額度兩倍以上**。Vercel 超額不是收錢而是**暫停專案**——字幕會在會議中途整個停掉。這條路不要走。
- **外包給 Ably／Pusher**：觀眾直連 Ably，Vercel 只做短請求。這條**真的可行且免費額度夠用**（10／200 連線、21 萬／600 萬則訊息），架構也漂亮。要離開 Render 的話走這條。

選 Render 的理由是：常駐 Node 行程**對長連線不設固定時長上限**，程式碼零改動即可運作，而且少一個服務就少一個活動前沒排練過的故障點。10 個觀眾的規模，用不到 Ably 的擴展能力。

### 步驟

1. 把這個資料夾推到 GitHub（`.gitignore` 已排除 `.env` 和 `transcripts/`，**API key 不會被上傳**）
2. Render → **New → Blueprint** → 選這個 repo
3. Render 讀到 `render.yaml` 會自動建好服務，並**跳出來問你四個祕密變數**：

   | 變數 | 填什麼 |
   | --- | --- |
   | `DEEPGRAM_API_KEY` | Deepgram 的 key |
   | `GEMINI_API_KEY` | Gemini 的 key |
   | `ROOM_CODE` | 自己訂，例如 `SHOW`（觀眾要輸入的） |
   | `OPERATOR_KEY` | 自己訂一組長一點的密碼 |

4. 部署完成後網址是 `https://<服務名>.onrender.com`

`render.yaml` 已設 `region: singapore`（離台灣最近的節點）與 `healthCheckPath: /healthz`。

### 免費方案的兩件事

**750 instance 小時／月。** 你的活動 7 天 × 6 小時 = 42 小時，用掉 5.6%，完全夠。

**閒置 15 分鐘會休眠，喚醒約 1 分鐘。** 活動進行中只要有觀眾連著就不會睡，會遇到的是每天第一次連線。做法：**開場前 2 分鐘先開一次收音頁**，或直接打 `https://<你的網址>/healthz` 把它叫醒。

不想管這件事就升 Starter（**$7／月**，永不休眠）。七天正式活動花 7 美金買「不用記得暖機」，我覺得值得，但不是必要。

### ⚠️ 逐字稿的持久性

**Render 免費方案沒有持久磁碟，實例一重啟 `transcripts/` 就整個消失。**

所以逐字稿改成三層保險：

1. 寫入 `transcripts/*.jsonl`（本機或有掛磁碟時最完整）
2. 伺服器記憶體保留整場（重啟前都讀得到）
3. **收音頁的瀏覽器 localStorage** ← 唯一能撐過伺服器重啟的一份

收音頁本來就會收到每一句的譯文，所以它自己存了一份完整副本，標題列的「💾 N 句」就是本機已保存的數量。按「下載逐字稿」是**直接從瀏覽器本機產生檔案，不經過伺服器**，所以雲端重啟過也還在。

**每天散會後按一次「下載逐字稿」**，這是唯一要記得的事。

## 已驗證 / 未驗證

**已測過：** 全部路由與權限檢查、路徑穿越防護、SSE 廣播、12 個同時觀眾全數收到、中途加入補看、`Last-Event-ID` 斷線補送、逐字稿存檔與下載、Gemini 與 Claude 兩條翻譯路徑的請求格式（以無效 key 打真實端點，回 401/API key not valid 而非格式錯誤）、`/healthz`、Render 模式開機輸出、磁碟消失後改讀記憶體的 fallback、收音頁重新整理後從 localStorage 還原逐字稿。

**未測過（需要真的 key 或真的環境）：**

- **Deepgram 實際串流**——沒有 key，整條 `/v1/auth/grant` → WSS → PCM 的路徑只有程式碼層面正確，沒有跑過真音訊。
- **實際翻譯品質**——需要真 key 才能看台灣用語提示詞的效果。
- **Service Worker 註冊**——程式與伺服器設定正確（`/sw.js` 從根路徑供應，scope 涵蓋 `/`），但我這邊的內嵌瀏覽器擋掉 SW 註冊，沒能實地驗證。註冊失敗已被 catch 吞掉，不影響字幕功能，只可能影響 Android Chrome 的安裝提示。
- **iOS Safari**——沒有實機可測。
- **SIGTERM 優雅關閉**——程式已接上，但 Windows 的 `kill -TERM` 不會真的把訊號交給 Node，所以在這裡驗不出來；Linux（Render）上才是真實行為。就算沒生效也只是觀眾多等幾秒重連，不影響正確性。
